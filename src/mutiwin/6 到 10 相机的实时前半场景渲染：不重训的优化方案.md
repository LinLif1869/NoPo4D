# 6 到 10 相机的实时前半场景渲染：不重训的优化方案

Oct 15, 2026 · @sptvet

## 结论：不要把 6 到 10 台一次塞进前馈，改成"重叠窗口 + 只算要用的视图"

你们自己的实验已经给出了方向：4 台高重叠相机（窗口 B）输入视角重建 27.44 dB，一次放 6 台降到 20.61 dB，原因是低重叠的端点相机（39↔40 估计重叠只有 0.13）在编码器的跨视图注意力里污染了整个场景特征，渲染阶段的 source culling 撤销不了。所以扩展的单位应该是局部窗口，而不是全局输入的相机数。

不重训的做法分五步，前两步决定能不能成，后三步决定能不能实时：

1. **选机位**：相邻相机光轴差约 9° 以内，估计重叠才能保持在 0.5 以上（按你们报告里的数对：7.2° 对 0.70，8.8° 对 0.51，16.7° 对 0.24）。按这个间距，6 台大约覆盖 45°，10 台大约覆盖 81°。
2. **滑动窗口**：4 台相机一个窗口，相邻窗口共享 2 台。每台物理相机只在一个窗口里充当"源"，所以总高斯数不会随窗口数翻倍。
3. **用共享相机做跨窗口对齐**：同一台相机在两个窗口里各预测一张深度图，两张图的比值直接给出窗口间的尺度残差，也能量化接缝处的不一致。你们现在的全局尺度对齐只用了标定基线，这一步是它的补充。
4. **只对要用的视图跑后半段网络**：Gaussian 头、速度头、深度头和运动注意力都是逐帧（或逐帧对）独立的，而你们的 source culling 每个窗口只用 16 个视图里的 1 个，其余 15 个视图的这部分计算是白算的。
5. **降帧数、降分辨率、窗口并行、延迟隐藏**：把一次窗口前馈压到几百毫秒量级，再靠多卡或批处理并行多个窗口。

两点说明：我这里没有 GPU，下面所有速度数字都是按你的实测值（4090 上 4 相机×4 帧 1.68 秒）和代码结构做的估算，会明确标注，最终以你自己 profile 的数为准；稀疏注意力掩码这一项是改了推理分布的做法，我没有任何实测，需要先按"实验矩阵"一节的指标验证。

## 架构一图：窗口化的 10 相机推理

每台相机只归一个窗口负责渲染，相邻窗口共享两台相机，窗口之间互不做注意力。

&#91;embedded content: 10 相机的窗口化架构 · 4 个窗口，每台相机一个负责窗口\]

以 10 台相机为例：4 个窗口每次前馈互相独立（可以批处理或分卡并行），每个窗口只渲染自己负责的相机对应的视角；共享相机在两个窗口里各有一张深度图，用来做尺度对齐。相机编号按沿方位角排好的链从 1 到 10。

## 机位设计：相邻重叠 0.5 以上，6 台约 45°，10 台约 81°

相邻相机的估计重叠要保持在 0.5 以上，这是你们报告里给出的门槛（理想 0.6 以上）。你们已有的数对说明，光轴差 9° 左右是这条线：

| 相机对 | 光轴差 | 估计重叠 | 说明 |
| --- | --- | --- | --- |
| 64↔65 | 2.0° | 0.86 | 窗口 A 内部 |
| 40↔64 | 7.2° | 0.70 | 窗口 A 内部 |
| 65↔41 | 8.8° | 0.51 | 刚好在门槛上 |
| 41↔42 | 16.7° | 0.24 | 窗口 A 与 B 之间的缝 |
| 39↔40 | 19.8° | 0.13 | 6 相机实验里把 PSNR 拉到 20.61 dB 的端点 |

按相邻间距 9° 估算（【推断】线性外推，实际取决于每台相机的 FOV 和俯仰），N 台相机能覆盖约 (N−1)×9°。用 4 台一窗、相邻窗口共享 2 台的滑动方式，窗口数 = (N−4)/2 + 1：

| 相机数 N | 约覆盖角度 | 窗口数 | 每次刷新要跑的前馈次数 |
| --- | --- | --- | --- |
| 6 | 45° | 2 | 2 |
| 8 | 63° | 3 | 3 |
| 10 | 81° | 4 | 4 |

你们现在的 8 台（A 窗口 40、64、65、41，B 窗口 42、66、67、43）物理上已经跨 52°，问题出在 41↔42 这条 16.7° 的缝：两侧重叠只有 0.24，缝附近的背景几乎没有共同观测，窗口间也没有共享相机可以做尺度对齐。优先补一台桥接相机，让它和 41、42 的重叠都不低于 0.5。

### 用你们的 select\_cameras 找桥接相机和扩展链

先看和 41、42 重叠最大的相机，再评估候选链：

```bash
python src/select_cameras.py --calibration src/calibration_results-19-11-12_ByteDT.json --neighbors 41
python src/select_cameras.py --calibration src/calibration_results-19-11-12_ByteDT.json --neighbors 42
python src/select_cameras.py --calibration src/calibration_results-19-11-12_ByteDT.json \
    --evaluate_ids 41,<候选>,42 --focus_ids 40,64,65,41,42,66,67,43
```

要从 69 台里自动沿方位角拼一条链，可以复用你们的 `Geometry.overlap`，再调用配套的 `multiwindow_utils.py`：

```python
import numpy as np
from pathlib import Path
from select_cameras import load_cameras, estimate_focus, Geometry
import multiwindow_utils as mw

cams = load_cameras(Path("src/calibration_results-19-11-12_ByteDT.json"))
focus, _ = estimate_focus([cams[i] for i in (40, 64, 65, 41, 42, 66, 67, 43)])
geo = Geometry(cams, focus, None)
centers = np.stack([c["C"] for c in geo.cams])
up = -np.mean([c["R"][1] for c in geo.cams], axis=0)       # OpenCV 的 y 轴朝下

# 只在你想用的候选里选（例如同一排、距离相近的相机），再按方位角排序
cand = [geo.index[i] for i in candidate_ids]
order = np.array(cand)[mw.azimuth_order(centers[cand], focus, up)]
chain = mw.greedy_chain(order, geo.overlap, min_overlap=0.5)
print([geo.ids[i] for i in chain])                         # 相机编号链
windows = mw.make_windows(len(chain), window=4, stride=2)
```

`greedy_chain` 每一步选满足重叠门槛的最远一台，让每台相机贡献尽量多的角度；中间出现断档就会在断档处停下，这正好告诉你哪里需要补相机。`select_cameras` 的重叠估计同时考虑水平和俯仰（水平重叠乘垂直重叠），所以候选里混了不同排的相机时，俯仰差大的会自然被排除。

### 垂直方向别忽略

你们相机的垂直视场约 17°（水平 22°、4:3 画幅）。人和桌面在竖直方向占的角度往往比这大，选相机时用 `--subject_radius` 把主体半径（标定单位）带上，让脚本检查主体外沿是否被裁出画面。主体贴边是新视角出现白边的另一个来源。

### 窗口怎么分工

每台物理相机只由一个窗口"负责"渲染，规则是优先选这台相机处于窗口内部（两侧都有邻居参与注意力）的窗口，链两端的相机只能由端窗口负责。N = 10 时分工是：窗口 0 负责链上第 0、1、2 台，窗口 1 负责第 3、4 台，窗口 2 负责第 5、6 台，窗口 3 负责第 7、8、9 台（`owner_window` 的输出，已测试）。这条规则是我按"两侧有上下文"做的选择，不是实测结论；你的窗口 B 实测里两端相机反而比中间两台 PSNR 更高（28.5 对 26.3 dB 左右），所以建议先用逐相机的输入视角 PSNR 验证，必要时手动改分工。

## 推理侧改造：窗口批处理、局部系渲染、共享相机对齐

核心思路是把 N 台相机拆成多个 4 相机窗口，窗口之间互不做注意力，等价于一个按窗口分块的块对角注意力。下面先说为什么不用稀疏注意力掩码，再给出窗口方案的四个改造点。

### 为什么不用稀疏注意力掩码

你上传的 DA3 代码里 `process_attention` 确实支持 `attn_mask`，但直接用来做 10 相机的稀疏跨视图注意力不现实：

- 你们的 `BackboneDA3.aggregator` 没有把 `attn_mask` 转发给骨干，需要自己加。
- `attention.py` 把 (B, N, N) 的掩码复制成 (B, 头数, N, N) 再交给 SDPA。以 504×378 输入为例，每个视图约 36×27 = 972 个 patch 加几个特殊 token，16 个视图约 1.56 万个 token，N² 约 2.4e8，布尔掩码约 243 MB，复制到 16 个头就是约 3.9 GB（每个全局层都要）。10 台相机 × 3 帧约 2.9 万个 token，复制后约 13.6 GB，4090 的 24 GB 显存基本放不下。
- 带显式掩码的 SDPA 不能走 flash 内核，会更慢。

（以上 token 数是我按分辨率和 patch 大小估算的，特殊 token 数以你的配置为准。）窗口批处理在数学上就是块对角掩码，但不占 N² 的掩码内存，所以直接按窗口分批。

### 改造点一：按窗口批处理，并修掉一个批内中位数的坑

模型本身支持 batch 维：把每个窗口当成 batch 里的一个样本，输入形状 (W, 4×F, 3, H, W)，`num_cameras=4`。需要先改一处：你们的 `normalize_extrinsics` 用 `torch.median(dists)` 对整个 batch 取一个中位数，批里有多个窗口时，各窗口会共用同一个归一化尺度，窗口 B 的尺度被窗口 A 带偏。改成逐样本取中位数：

```python
def normalize_extrinsics(ex_t, min_dist=1e-1):
    transform = affine_inverse(ex_t[:, :1])
    ex_t_norm = ex_t @ transform
    c2ws = affine_inverse(ex_t_norm)
    dists = c2ws[..., :3, 3].norm(dim=-1)                                   # (B, V)
    median_dist = dists.flatten(1).median(dim=1).values.clamp(min=min_dist) # (B,)
    ex_t_norm[..., :3, 3] = ex_t_norm[..., :3, 3] / median_dist[:, None, None]
    return ex_t_norm
```

你们 `_predict_camera_poses` 里的深度尺度估计本来就是按 batch 逐样本算的，不用改。改完后做一个检查：把同一个窗口复制成 B=2，每个样本的归一化结果应与单独跑 B=1 完全相同。

批处理的输入构造如下（`images` 为 \[相机, 时间, 3, H, W\]，`w2c`、`K` 为每台相机的标定）：

```python
windows = mw.make_windows(N, window=4, stride=2)
batch_imgs = torch.stack([images[w].flatten(0, 1) for w in windows])          # (W, 4*F, 3, H, W)
batch_w2c  = torch.stack([w2c[w].repeat_interleave(F, 0) for w in windows])   # (W, 4*F, 4, 4)
batch_K    = torch.stack([K[w].repeat_interleave(F, 0) for w in windows])
ts = torch.linspace(0, 1, F).repeat(4)[None].expand(len(windows), -1)
out = model(batch_imgs, timestamps=ts, num_cameras=4,
            input_extrinsics=batch_w2c, input_intrinsics=batch_K)
```

### 改造点二：每个窗口在自己的局部系里渲染，不搬运高斯

每个窗口的高斯都在它自己的归一化系里：以窗口第一台相机为原点，平移除以中位距离 m。不需要把高斯（均值、尺度、旋转、速度、角速度）逐个变换到世界系。更简单的做法是反过来：把世界系的目标相机变到各窗口的局部系，每个窗口直接用你现有的 `Scene.render` 渲染，再在图像空间合成。

```python
ex, m, first_c2w = mw.normalize_w2c(w2c_window_repeated)     # 必须传 V = 4×F 个视图（相机各重复 F 次）
tgt_local = mw.camera_world_to_local(target_c2w_world, m, first_c2w)
```

`normalize_w2c` 复刻了 `normalize_extrinsics` 的算法（含 `torch.median` 偶数个取较小者）。我测试了：第一台相机变成单位位姿，世界点与局部点往返一致，局部深度乘 m 等于世界深度，目标相机变换后同一世界点的深度一致；但我没有在 torch 里和你们的函数逐项对拍，改完后请自己对拍一次。

### 改造点三：共享相机做窗口间尺度残差

窗口 i 和窗口 i+1 共享的相机，在两个窗口里各有一张深度图。换成世界单位后取比值，就是这两个窗口之间还剩多少尺度不一致：

```python
r = mw.shared_camera_residual(depth_i, m_i, depth_next, m_next, valid=conf_mask)
# r["scale_b_to_a"]：下一个窗口的深度相对当前窗口应乘的系数
# r["log_mad"]：log 比值的离散度，越大说明接缝处两窗口的几何越不一致
```

建议分两步用：第一步只当诊断，对每条接缝打印 `scale_b_to_a` 和 `log_mad`。你们的全局基线尺度已经把深度对齐到标定了，所以这个残差如果长期接近 1，说明窗口间已经一致；如果某条接缝稳定偏离（比如超过 3%，这个阈值是我的建议），再考虑把残差乘进该窗口的 `depth_scale`，从窗口 0 往外累乘。注意深度比值只在两窗口都有可靠深度的像素上有意义，`valid` 建议用深度置信度或 alpha 做掩码。

### 改造点四：相邻窗口之间平滑合成

对世界系里的每个目标视角，算它的方位角，用 `blend_weights` 在相邻两个负责相机之间给出权重，只在过渡带内混合，其余位置只用最近的负责窗口：

```python
w = mw.blend_weights(view_angle, owner_angles, width=transition_deg)
color = sum(wi * alpha_i * color_i for wi, alpha_i, color_i in parts)
alpha = sum(wi * alpha_i for wi, alpha_i, _ in parts)
color = color / alpha.clamp_min(1e-4)                       # 预乘合成后还原
```

这和你们已有的 `render_path_fused` 思路一致，区别只是融合对象由"同一窗口里的两台源相机"变成"相邻两个窗口的负责相机"。过渡带宽度建议先取 3° 左右，用接缝处的视觉连续性和 alpha 覆盖率来调。

还有一个收益：当相邻窗口在世界系里几何一致（上一步残差接近 1）时，一个窗口里 alpha 很低的空洞，可以用邻窗口同一位置的内容去填。你们报告里 `nearest_fill` 当时不稳定、没法当默认值，很可能就是因为两个来源的深度尺度没有被统一约束。这一点是我的推断，需要在接缝处实测。

## 实时化：瓶颈在前馈，最大的杠杆是帧数和"只算要用的视图"

渲染本身已经够快（每帧 2.6–2.8 ms），要砍的是一次窗口前馈的 1.68 秒。我按你的代码结构估算了各部分的计算量，下面的数字都是估算，不是实测，请先用本节末尾的计时代码把真实分布测出来。

### 计算量估算（只算矩阵乘，不含 DPT 头）

假设：输入 504×378，每个视图约 36×27 = 972 个 patch 加 1 个时间 token；骨干 24 个 block、维度 1024，其中 8 个全局注意力、16 个视内注意力；运动编码器每个导出层 1 个 block、维度 2048、MLP 比 4，相邻帧对里所有相机的 token 一起做注意力。

| 输入配置（每窗口 4 相机） | 视图数 | 骨干 + 运动编码器（TFLOPs） | 相对现状 |
| --- | --- | --- | --- |
| 4 帧（现状） | 16 | 33.7（骨干 18.3，运动 15.3） | 100% |
| 3 帧 | 12 | 22.5 | 67% |
| 2 帧 | 8 | 12.3 | 36% |
| 1 帧（静态，无运动编码器） | 4 | 3.1 | 9% |
| 3 帧，392×294 | 12 | 11.4 | 34% |
| 1 帧，392×294 | 4 | 1.7 | 5% |

两个结论：运动编码器的计算量和骨干同一个量级（15.3 对 18.3），因为它在每个相邻帧对上对 2·C·N 个 token 做联合注意力，帧数从 4 降到 1 时它整个消失；总计算量对帧数是超线性下降的，因为全局注意力是平方项。

如果把 33.7 TFLOPs 按 30–50 TFLOPs 的有效吞吐折算（吞吐是我假设的），纯 transformer 部分约 0.7–1.1 秒，那么 1.68 秒里剩下的 0.6–1 秒很可能花在全分辨率 fp32 的 DPT 头（高斯头、两个方向的速度头、深度头）和反投影上。这是推断，需要 profile 确认。

### 优化阶梯（按收益排序，除标注外都不改变模型权重）

| 手段 | 做法 | 估计收益 | 画质风险 |
| --- | --- | --- | --- |
| 1. 头部只算要用的视图 | 你们 source culling 每窗口只用 16 个视图里的 2–3 个，高斯头、速度头、深度头都是逐帧独立的，只对负责相机的源时刻视图跑 | 头部计算降为约 1/6 到 1/8 | 无，应与全量结果逐像素一致，需对拍 |
| 2. 运动编码器只算要用的帧对 | 源时刻的前向和后向各需要一个相邻帧对，其余帧对（逐对独立）跳过 | 4 帧时帧对 3→2；固定时间渲染时可整个跳过 | 无 |
| 3. 头部改 bf16 | 骨干已是 bf16，头部在 `autocast(enabled=False)` 下跑 fp32 | 头部约 1.5–2 倍（估） | 低，需看 PSNR 是否变化 |
| 4. 降到 3 帧或 2 帧 | 源时刻放中间，3 帧即可同时有前后向邻居 | 见上表，22.5 或 12.3 TFLOPs | 中，需验证运动质量 |
| 5. 固定时间渲染用 1 帧静态模式 | 代码里 `timestamps=None` 或每相机 1 帧时运动输出为零，不跑运动编码器 | 骨干降到 3.1 TFLOPs | 中到高，模型训练时没见过多相机单帧，必须用输入视角 PSNR 验证 |
| 6. 降分辨率 | 504×378 → 392×294 | 再降约 40–50% 的 transformer 计算 | 中，窄视场下细节损失 |
| 7. 窗口并行 | N=10 有 4 个窗口，分到多张卡，或用 CUDA stream | 窗口数对延迟的影响变成 1 | 无 |
| 8. `torch.compile` / CUDA Graph | 形状固定（固定窗口数、帧数、分辨率）时收益明显 | 通常 1.1–1.3 倍（经验值） | 无 |

手段 5 值得单独说明：如果你的实时目标是"每次刷新重建当前时刻，视角自由移动"，时间轴上不需要渲染其他时刻，那么运动本来就用不上（固定时间渲染时 Δt=0，速度不起作用，你们报告里 `anchor_time` 就是这样用的）。4D 运动的价值在于两次刷新之间做外推，见下面的延迟隐藏。

手段 1 和 2 的改法：高斯头、速度头、深度头的输入是 token 列表和图像，可以在调用前沿视图维度切片，同时把相机位姿、深度、时间戳也切成同样的视图子集；运动编码器的 `_run_motion_blocks` 里帧对是批处理的，把 `P` 限制到需要的帧对即可，输出里不需要的位置保持零，再切片。改完务必做一次对拍：同一输入下，选中视图的深度、高斯参数与改前全量结果的差应在 bf16 数值误差内。

### 进阶：静态背景缓存 + 动态区域裁剪（未验证）

人和桌面的前半部分里，桌子、背景基本静止，会动的只有人和手。一种做法是：用整幅图的 1 帧静态模式重建一次背景并缓存，运行时只对手和人所在的区域做裁剪重建（裁剪后分辨率小、token 少，内参相应平移），渲染时按深度和 alpha 叠在背景上。这个思路能把每帧的计算量再降一个数量级，但需要一个轻量的人/手区域跟踪，也需要两套高斯在深度上一致，这些我都没有验证，建议放在前面几步稳定之后再试。

### 流水线与延迟隐藏

- 渲染线程始终渲染最近一份完成的场景，编码线程在后台算下一份，两者不互相等待。
- 如果用 4D 模式（≥2 帧），可以用速度把高斯从源时刻外推到当前时刻，补偿编码延迟。外推只适合很短的时间窗，范围要靠实测确定；你们的 `temporal_opacity_mode=constant` 已经避免了外推时不透明度衰减。这条是推断，未验证。
- 多窗口交错启动：窗口 k 比窗口 k−1 晚启动一个固定相位，使画面的各部分更新时间错开，而不是每个周期集中卡一次。

### 先测再改：分阶段计时

```python
import time, torch
from contextlib import contextmanager

@contextmanager
def timed(name, store):
    torch.cuda.synchronize(); t0 = time.perf_counter()
    yield
    torch.cuda.synchronize(); store[name] = store.get(name, 0.0) + (time.perf_counter() - t0)

# 在 encoder._run_heads / forward 里包住各阶段，例如：
#   with timed("backbone", T):     layers_tokens = self._run_backbone(scene_input)
#   with timed("cam+depth", T):    camera_pose, depth_scale = ...; depth = ...
#   with timed("motion_blocks", T): ...
#   with timed("velocity_head", T): ...
#   with timed("gaussian_head", T): ...
# 预热 1 次后跑 3 次取中位数，打印 T，再决定先砍哪一块
```

如果测出来头部（高斯头加速度头加深度头）确实占 0.6 秒以上，手段 1、2、3 的收益就最大；如果骨干加运动编码器占大头，则手段 4、5、6 是主要杠杆。

## 实验矩阵：每一步用什么数判断有效

沿用你们的原则：输入视角重建 PSNR 没对齐之前，不要看渲染视频。下面按依赖顺序排，前一步不过关不进下一步。通过线是我按你们窗口 B 的实测（整体 27.44 dB，逐相机 26.3–28.6 dB）和 6 相机失败案例（20.61 dB）设的建议值，不是标准。

| 步骤 | 改动 | 主要看什么 | 建议通过线 |
| --- | --- | --- | --- |
| E0 | 4 相机现状，加分阶段计时 | 骨干、运动编码器、各头、反投影各占多少秒 | 总和与 1.68 秒基本吻合 |
| E1 | 窗口批处理，修 `normalize_extrinsics` 的批内中位数 | B=2 复制同一窗口，与 B=1 逐样本对拍 | 归一化尺度和输出一致到数值误差 |
| E2 | 现有窗口 A 和 B 一起批处理 | 逐窗口输入视角 PSNR 与单独跑是否一致 | 与单独跑相差不超过 0.3 dB |
| E3 | 补桥接相机或重选链，让每条相邻重叠 ≥ 0.5 | 接缝相机的 `scale_b_to_a` 与 `log_mad` | 尺度在 ±3% 内，`log_mad` 小（先记录，再定线） |
| E4 | 头部只算负责视图，加 bf16 | 与全量结果对拍；PSNR；耗时 | 深度和高斯参数差在 bf16 误差内，PSNR 变化小于 0.2 dB |
| E5 | 4 帧降到 3 帧、2 帧 | 逐相机 PSNR；人和手的运动是否仍连贯 | PSNR 下降小于 0.5 dB |
| E6 | 每相机 1 帧静态模式 | 逐相机 PSNR；Alpha 覆盖 | 整体 ≥ 26 dB，否则放弃手段 5 |
| E7 | 392×294 | PSNR；人物边缘和手指细节目测 | PSNR 下降小于 1 dB |
| E8 | 窗口并行 + 渲染线程分离 | 端到端刷新周期、渲染帧率、接缝视觉连续性 | 刷新周期达到你定的实时目标，渲染不掉帧 |

三类指标的具体读法：

- **逐相机输入视角 PSNR**：沿用 `--recon_check`。6 相机失败时，逐相机里最低的两台只有 17.1、17.5 dB，整体 20.61 dB 掩盖了这一点，所以逐相机比整体更能暴露问题。
- **接缝一致性**：共享相机的 `scale_b_to_a` 反映两个窗口的整体尺度差，`log_mad` 反映像素级几何不一致。它们和 PSNR 互补，PSNR 只看输入视角，接缝问题常常到新视角才暴露。
- **Alpha 覆盖**：沿用你们的 `--save_alpha`，在整个前半场景的视角范围内统计 alpha<0.5 的像素比例。单窗口 8° 轨迹两端是约 8%，多窗口拼接后的整体不应比这更差；接缝处单独看一遍。

每一步只改一个变量，记录 PSNR、耗时和接缝指标三列。E4 到 E7 之间的组合可以在各自单独通过后再叠加，叠加时重新回到 E0 的计时，确认节省没有互相抵消。

## 风险与未验证项

- **所有速度数字都是估算**。我没有 GPU，计算量按你的代码结构和输入尺寸推算，有效吞吐是假设值。优化阶梯的收益排序可能因 profile 结果而改变。
- **配套代码只测了 numpy 部分**。`multiwindow_utils.py` 的窗口划分、坐标互转、共享相机残差、融合权重都有单元测试并通过；文档里的 torch 代码片段（批处理构造、逐样本中位数、分阶段计时）我没有运行过，也没有接进你们的 `inference.py`。
- **窗口批处理要先对拍**。`normalize_w2c` 是按你们 `normalize_extrinsics` 的算法复刻的，需要在 torch 里逐项对拍；B>1 时还要确认其余环节（高斯切片、`Scene.render` 对 batch 维的处理）没有隐含 B=1 的假设，我只读了 encoder、解码器和 `Scene` 的主干部分，没有通读 1,800 行的 `inference.py`。
- **窗口分工规则未验证**。"内部相机优先"是我按两侧有上下文做的选择，你自己的窗口 B 实测里两端相机反而更高，请用逐相机 PSNR 决定。
- **1 帧静态模式和 3、2 帧模式是分布外用法**。论文训练时每批 16 帧、1–4 个相机（阶段一是单相机），多相机单帧没有被专门训练过，质量只能靠输入视角 PSNR 验证。
- **共享相机残差修正可能引入新误差**。深度比值只在两窗口都可靠的像素上有意义；先只做诊断，不要一上来就把残差乘进深度。
- **窄视场和遮挡后空洞是物理上限**。更多窗口扩大的是可观察的视角范围，不会让某个视角下被遮挡的背景凭空出现。每个窗口内部的白边仍然存在；用邻窗口填洞依赖几何一致性，需要在接缝处实测。
- **窗口之间仍不是统一的 3D 场**。和你们的宽范围页面一样，相邻窗口之间是带过渡的物理视角切换，不是无缝的自由飞行。
- **相机越多，同步和标定误差越容易暴露**。每台相机的时间戳偏差、标定残差都会在接缝处放大，建议扩展前先检查新加相机的同步。
- **延迟隐藏里的速度外推没有验证**。外推的有效时间范围需要实测，大位移区域（快速手部运动）论文也列为失败案例。
